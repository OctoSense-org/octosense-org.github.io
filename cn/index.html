当前代码中的架构

一个 Shell，各有职责的 Agent

OctoSense 托管应用，并把它们接入共享的 octos Agent 内核。Agent 是由模型驱动、处理请求并使用获授权工具的协作方；应用操作由 Shell 检查并执行。

系统助手

你可以让系统助手协调工作。它会向已获允许的应用 Agent 求助，再获取结果。

应用自己的 Agent

声明了 Agent 访问或工具的应用，经你同意后可以获得 Agent。Shell 按应用与账号准备称为 peer 的身份，其工具与数据访问都有明确范围。

也可以直接问应用

桌面端的 “Ask <app>” 打开应用 Agent 的对话。你的对话与系统助手委派的任务各有记录，可以并行运行。

跟随一个日历问题

在桌面端，配置模型并同意使用 Calendar 的 Agent 后，“我今天有哪些日程？”可以走两条路线。模型可以调用日历事件工具，读取宿主管理的日历。

直接问应用

在桌面端的 Ask Calendar 中问“我今天有哪些日程？”。配置模型并获得同意后，应用 Agent 可以调用日程工具，答案回到你的对话。

  1. 你向 Calendar 提问. Shell 的 Ask-app 面板通过应用专属 broker 发送消息。手机触控导航尚无打开此面板的入口。
  2. 你的应用对话. Shell 在 Calendar 的应用/账号 peer 上打开 context，即独立的一条对话。模型回合使用应用获授权的工具。该 context 保存独立记录，与系统委派工作分开。
  3. Calendar 读取日程. 如果模型调用 calendar.events，Shell 检查调用并交给 Calendar 的 Rust 宿主服务。服务读取自己的 calendar/events.json；模型不会因此获得通用数据库访问权。
  4. 你收到答案. 工具结果回到应用的模型回合，回复事件再经你的用户 context 返回 Ask Calendar 面板。这不会自动启动系统 Agent 的回合。

系统委派

系统助手可以把同一个问题委派给 Calendar 的 Agent。它使用同一应用/账号 peer 上的另一条对话，获取结果后再回答你。

  1. 系统助手委派任务. agents.list 发现应用 Agent；需要时，agents.ask 请求同意并等待 peer 就绪。peer_send_input 使用内核返回的 peer 标识符提交任务。
  2. Calendar 的系统通道. 内核将 peer/input 发给 Shell broker，由它启动 Calendar 回合，这条系统通道是 peer 用于委派工作的对话。独立的用户 context 可以同时运行；两者各自保存记录。
  3. Calendar 读取日程. 应用模型可以请求已声明的 calendar.events 工具。Shell relay 检查授权并交给所属服务，JSON 结果回到该应用回合。
  4. 系统助手回答. Calendar 完成的答案记录在内核的 peer 黑板中。系统助手用 peer_gather 获取结果，在系统聊天中回答。目前没有通用的应用到系统 Agent 委派 API。工具审批走另一条由宿主控制的路线。

Rust 执行

跟随一个请求从 UI 进入 octos。箭头表示请求方向，回复沿这些边界返回。Peer 是持久身份，并非一个进程、线程或 Tokio task。

  1. 应用与 Shell UI. 原生 Rust 模块在 Shell 内运行；部分应用可以在子进程中运行。隔离的 main.splash 应用使用受限 Splash VM；L0 page.card 内容走独立的 Octoscript 解析与 lowering 路线。
  2. 应用 broker. Broker 是 Shell 的适配层，绑定应用/账号身份，并在获得同意后路由对话请求。每个 Broker 创建单工作线程的 Tokio runtime，处理请求与连接。多个 broker 可以共享一个持久 peer。
  3. 共享内核服务. Shell 内核服务让使用者共享同一代内核，由 supervisor 管理传输和进程生命周期。桌面使用内核子进程，OpenHarmony 在进程内嵌入；iOS 没有集成内核。
  4. octos 回合工作. octos 先创建暂停等待的编排 task；活跃回合准入成功后，oneshot 屏障才放行，开始 Driver 处理与工具 future。宿主工具调用经 broker 回到 Shell 执行器，结果让模型继续。这些 task 结束后，peer 仍然存在。

同一个 peer 可以服务这两条路线。每条对话保存自己的记录，也可以接收另一条对话近期历史的有限摘录。

数据访问取决于工具与账号

在 Unix 上，应用 Agent 可以用受限文件工具读取开放的账号工作目录，也可调用 calendar.events 等已实现的应用工具。它不会自动看到所有应用数据库和凭据。调用另一应用的工具，还需要宿主提供该工具、所有者声明可共享、调用方获得授权，并有实际执行器；审批遵循 Shell 的策略。

哪些已经实现，哪些仍是设想

News 提供读取与通知工具；桌面 Calendar 提供日程工具。Mail 的 Agent 目前通过 mail.notify 发布通知，其 UI 的读信和发信 API 尚未开放为 Agent 工具。应用包的自动触发器、由脚本实现的 Agent 工具，以及应用到系统 Agent 的通用委派仍未实现。本站的邮件和定时服务场景展示的是设想中的工作流。随产品提供的通知和日历卡片没有卡内对话；Mail 聊天演示使用预设回复。

开发者：应用托管与 Rust 执行方式

原生 Rust 应用

编译后的模块在 Shell 内运行；部分桌面应用可以作为子进程运行。模块和进程是不同的启动方式，并非每个 Agent 对应一个进程。

隔离脚本应用

App Hub 准入应用包后，由 Splash 隔离环境执行 main.splash。L0 page.card 应用包则走独立的 Octoscript 解析与 Makepad lowering 路线。Design Flow 的 tools/octo 命令启动 App Hub 的 card-host，适合检查本地 UI；该宿主没有 Shell 的宿主服务或 Agent。

Peer 与 Tokio task

Peer 是持久身份；session 保存对话，turn 处理一次输入。Tokio task 执行异步工作。Shell UI、broker runtime 和共享内核服务分别调度。一个 peer 并不等于一个线程或一个 task。

桌面版与 Android Home 共用 Rust Shell。OpenHarmony 在进程内运行内核；iOS 目前没有集成 Agent 内核。ROM 将 Home 与 Android 平台服务一起打包，其中的特权桥接服务不同于系统 LLM Agent。手机触控导航尚无打开 Ask-app 面板的入口。

再了解多一点

OctoSense 是一个新的操作系统吗？

OctoSense 是 Agent Shell，即传统操作系统之上的交互层。我们希望把应用、上下文和 Agent 能力，带进一个熟悉的入口，连接桌面与移动设备。

它与 AI 聊天应用有什么不同？

对话是表达意图的一种好方式。OctoSense 探索更丰富的可能：可交互卡片、应用、直接操作与熟悉的手势。Agent 参与塑造的不只是回答，还有工作区本身。

我还能直接操作应用吗？

当然，这正是我们的核心想法。你依然可以启动并亲手操作应用。Agent 的辅助应该建立在这种掌控感之上，让体验更有用。

用什么构建？是开源的吗？

octos 内核、Makepad UI 框架和 OctoSense Shell 以 Rust 构建。应用可使用 Splash 脚本或 Octoscript L0 卡片；Android 等平台集成还包含平台专用代码。各项目均开源，许可证以各仓库为准。

现在可以体验或参与吗？

可以。用 cargo 运行桌面版，在 Android 手机上安装 OctoSense Home 应用，或者给 OnePlus 6 刷入 OctoSense ROM；三者都从 OctoSense 仓库构建，那里有最新的构建说明。想动手做应用，从 OctoScript-App-Design-Flow 开始；Agentic App 黑客松是很好的起点。本站的交互预览使用示例数据来呈现理念，并非正在运行的 Agent。
